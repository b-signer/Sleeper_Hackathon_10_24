# WP1: GitHub data as of T

WP1 answers "what did this repo look like at time T?" accurately, cheaply and without leaking anything from after T. This is the critical path and the main source of backtest risk. Read `decisions.md` §4 (known traps) before starting.

---

### T1.1 GitHub access layer
**Goal:** One way to call GitHub (REST and GraphQL) that survives rate limits, caches everything, and can run fully offline.
**Implements:** C5, D12 · **Depends on:** T0.1 · **P0 · M**

**Done when:**
- Requests are authenticated with the configured token. A missing token fails with a clear message.
- The layer does not fail when rate limits run low or when GitHub returns rate-limit errors. It waits and retries within a bounded time, shown by a simulated test.
- Concurrency is bounded.
- Every response is cached on disk and the cache survives restarts. The same request is served from the cache.
  - Responses about the past (as of a backtest T) never expire.
  - Responses about the present expire after a few hours.
- The cache file can be copied to another machine and used there.
- In offline mode, a cache miss raises a distinct, clear error, and nothing touches the network.

**Out of scope:** what to fetch (T1.2–T1.7).

### T1.2 Stars as of T
**Goal:** For a repo and a T, report its stars at T and its star history before T.
**Implements:** F1.2, F1.6, F3.2, F3.3, C1 · **Depends on:** T1.1 · **P0 · M**

**Must provide:** stars at T; stars gained in the 30 and 90 days before T; monthly star totals for up to the last 12 month ends before T; the largest number of stars gained in one day in the 180 days before T, and the date it happened. It must also report quickly that a repo was **above the star range** at T without counting all of its stars.

**Done when:**
- Tests on fixture stargazer lists give correct results when T falls exactly on a page boundary, in the middle of a page, before the first star, and when the repo is above the range.
- The number of requests per repo stays bounded by the star range, **not** by the repo's current popularity. A repo with 50k stars today costs no more than one with 2,000.
- A live test: stars at T for 3 known repos are within 2% of an independent source (GitHub UI or a star-history chart).

**Hints:** stargazers can be read oldest first with their timestamps (A1), so you can find the T boundary with a binary search over pages. v0.2 §9.2 sketches this.

### T1.3 Activity as of T
**Goal:** Report a repo's development activity before T.
**Implements:** F1.2, F1.6, F3.2, F3.3, C1 · **Depends on:** T1.1 · **P0 · M**

**Must provide:**
- Commits in the 30 and 90 days before T, and weekly commit counts for the 12 weeks before T
- Distinct authors in the last 90 days, and the top author's share of commits in the last 365 days
- The last commit before T, and whether there is any commit before T at all
- Issues opened and closed in the last 90 days, open issues at T, and PRs merged in the last 90 days
- Releases published before T (drafts excluded), and the most recent one
- Repo age at T and license

**Done when:**
- Each metric is tested against fixture data.
- Values that can't be determined come back as unknown, never as guesses (F3.12).
- A live spot-check of `commits_90d` and the last commit for 3 repos matches GitHub.

**Hints:** batched GraphQL can cut request counts a lot. Commit authors without a GitHub account need some grouping rule.

### T1.4 README and description as of T
**Goal:** Provide the README as it was at T, and a short description made from it.
**Implements:** F3.4, F1.6, C1 · **Depends on:** T1.1 · **P0 · S**

**Done when:**
- The README text comes from the last commit before T, with the commit's ID and date. Badges, images and HTML noise are removed, and the length can be capped.
- The description at T is **extracted** from the README at T: the first few hundred characters of prose after the title, with badges removed. It is never generated by an LLM, which would cost money and could leak model knowledge into a backtest field. In backtest mode, it **never** uses the repo's current description or topics. Test this with a fixture where they differ.
- A live test: for a repo whose README changed after T, the README returned is the old one.

### T1.5 Future-data guard
**Goal:** Make look-ahead leaks fail loudly instead of corrupting results silently.
**Implements:** C1 · **Depends on:** T0.2 · **P0 · S** · *Never cut.*

**Done when:**
- In backtest mode, any **data** timestamp at or after T in a structured tool output fails the run with a clear error that names the field. Date-only and month values are compared as the T0.2 contract specifies.
- **Metadata** fields that legitimately equal T (for example `as_of`) do **not** trip the guard.
- Free-text README content is not scanned.
- Tests:
  - The leaky fixture fails.
  - A normal output with `as_of = T` passes.
  - A data timestamp exactly equal to T fails.

### T1.6 Live-mode data
**Goal:** The same data as T1.2–T1.4 when T is "now" (the time the live universe was built).
**Implements:** F1.3, F2.1 · **Depends on:** T1.2–T1.4 · **P0 · S** (the demo opens in live mode)

**Done when:**
- Live mode returns the same output shapes as backtest mode.
- Stars at T is the current count. Recent gains come from the most recent stargazers.
- Archived repos are excluded.

---

### T1.7 Contributors as of T
**Goal:** The top authors of a repo before T.
**Implements:** F3.7, C1 · **Depends on:** T1.1 · **P1 · S**

**Done when:**
- Returns up to 5 top authors with their commit counts and shares, first and last commit dates before T, and account creation date.
- Live mode may add current profile facts (followers, public repos, company). Backtest mode **must not**, and a test checks this.
